# Система учёта материалов

Внутренняя веб-система учёта материалов для производства: автоматический расчёт остатков по местам хранения, приход и списание материалов, контроль минимальных остатков, список «Требуется закупка», история операций и управление пользователями.

Система работает как одно веб-приложение (интерфейс и сервер вместе) плюс база данных PostgreSQL, доступ к которым закрыт прокси-сервером с HTTPS. Разворачивается на собственном сервере предприятия, доступ — только из локальной сети, интернет не требуется.

## Требования

На сервере должны быть установлены:

- **Docker** (версия 24 и новее)
- **Docker Compose** (входит в современные версии Docker как `docker compose`)

Больше ничего устанавливать не нужно — база данных PostgreSQL и сама система запускаются в контейнерах.

## Готовые варианты запуска

Один и тот же `docker-compose.yml` поддерживает два варианта — переключаются одной строкой `COMPOSE_PROFILES` в `.env`, без правки самого compose-файла:

| Вариант | `COMPOSE_PROFILES` в `.env` | Что запускается | Когда использовать |
|---|---|---|---|
| **Стандартный (по умолчанию)** | `proxy` | `db` + `app` + встроенный `proxy` (nginx с HTTPS на 80/443) | Обычный случай: на сервере кроме этой системы ничего не занимает 80/443 порты. Всё «из коробки», включая HTTPS. |
| **Без встроенного прокси** | *(оставить пустым)* | только `db` + `app`, приложение слушает `127.0.0.1:3000` | На сервере уже есть свой nginx/другой reverse proxy (например, для нескольких сайтов на одной машине) — настройте его на `127.0.0.1:3000`, а свой HTTPS-сертификат подключите там же. |

Чтобы использовать вариант «без прокси», в `.env` оставьте `COMPOSE_PROFILES` пустым (или удалите строку) и не выполняйте шаг с созданием сертификата ниже — он в этом варианте не нужен.

## Установка и запуск на сервере

1. **Скопируйте папку проекта на сервер** (например, через `git clone`, `scp` или архивом).

2. **Создайте файл `.env`** на основе `.env.example`:

   ```bash
   cp .env.example .env
   ```

3. **Заполните `.env`** реальными значениями:

   | Переменная | Как заполнить |
   |---|---|
   | `COMPOSE_PROFILES` | Оставить `proxy` (по умолчанию) для варианта со встроенным HTTPS, либо оставить пустым для варианта со своим reverse proxy — см. [«Готовые варианты запуска»](#готовые-варианты-запуска) |
   | `POSTGRES_PASSWORD` | Придумайте надёжный пароль для базы данных |
   | `AUTH_SECRET` | Сгенерируйте случайную строку: `openssl rand -base64 32` (или `npx auth secret`) |
   | `AUTH_URL` | Адрес, по которому система будет доступна в сети предприятия, обязательно с `https://`, например `https://materials.company.local` или `https://192.168.1.10` |

   Строку `DATABASE_URL` в `.env` менять не нужно — контейнер приложения обращается к базе данных внутри Docker-сети по имени `db`, а не по значению из `.env` (оно используется только при запуске скриптов вне Docker, см. раздел [«Разработка»](#разработка)).

4. **Создайте сертификат для HTTPS** — нужен только для стандартного варианта (со встроенным прокси); если у вас вариант «без прокси», пропустите этот шаг. См. раздел [«HTTPS и сертификат»](#https-и-сертификат) ниже — для внутренней сети достаточно одной команды с самоподписанным сертификатом.

5. **Запустите сборку и старт контейнеров**:

   ```bash
   docker compose up -d --build
   ```

   При первом запуске это: соберёт образ приложения, запустит базу данных, дождётся её готовности, автоматически создаст структуру базы данных (таблицы, индексы) и запустит само приложение (и прокси-сервер с HTTPS, если используется стандартный вариант). База данных при этом создаётся **пустой** — без каких-либо учётных записей или материалов.

6. **Проверьте, что всё запустилось:**

   ```bash
   docker compose ps
   docker compose logs -f app
   ```

   Контейнеры `db` и `app` (и `proxy`, если он используется) должны быть в состоянии `Up`/`healthy`.

7. Откройте систему в браузере по адресу, указанному в `AUTH_URL`. В стандартном варианте это просто `https://адрес` — отдельно указывать порт 443 не нужно; браузер один раз предупредит о недоверенном сертификате, если он самоподписанный — это нормально для внутренней сети, нужно подтвердить продолжение («Дополнительно» → «Всё равно перейти»). В варианте без встроенного прокси адрес и порт зависят от настройки вашего reverse proxy. Вы увидите страницу входа — на этом этапе войти пока нельзя, потому что в базе данных ещё нет ни одного пользователя. Перейдите к следующему шагу.

## HTTPS и сертификат

Этот раздел касается только стандартного варианта запуска (со встроенным прокси, `COMPOSE_PROFILES=proxy`) — за HTTPS отвечает `nginx` (сервис `proxy` в `docker-compose.yml`), который принимает соединения на 443 порту и передаёт запросы приложению внутри Docker-сети. Если вы используете вариант без встроенного прокси, HTTPS настраивается на вашем собственном reverse proxy — этот раздел можно пропустить.

Файлы сертификата (`server.crt`, `server.key`) кладутся в `docker/certs/` — в репозитории эта папка пустая (сертификат и ключ — секрет конкретного сервера, в git не хранятся), поэтому создать их нужно один раз при установке. Есть два варианта:

- **Самоподписанный сертификат (проще, подходит для внутренней сети предприятия).** Браузер один раз спросит подтверждение при первом заходе — это нормально для внутренней сети без доступа из интернета. Создаётся одной командой на сервере:

  ```bash
  openssl req -x509 -nodes -newkey rsa:2048 \
    -keyout docker/certs/server.key \
    -out docker/certs/server.crt \
    -days 825 -subj "/CN=materials-tracker.local"
  ```

  Если на сервере нет `openssl`, можно выполнить ту же команду через Docker: `docker run --rm -v "$(pwd)/docker/certs:/certs" alpine/openssl req -x509 -nodes -newkey rsa:2048 -keyout /certs/server.key -out /certs/server.crt -days 825 -subj "/CN=materials-tracker.local"`.

  Прокси-сервер настроен принимать соединения по имени/адресу сервера (`server_name _`, то есть любой адрес), поэтому конкретное имя в сертификате менять не обязательно — можно оставить как в примере.

- **Настоящий сертификат** (если у предприятия есть свой домен и сертификат, например от внутреннего удостоверяющего центра). Положите свои файлы в `docker/certs/` под именами `server.crt` и `server.key` (или под своими именами, обновив пути `ssl_certificate`/`ssl_certificate_key` в `docker/nginx.conf`).

После того как файлы сертификата на месте, запустите (или перезапустите) прокси: `docker compose up -d --build proxy`.

## Создание первого администратора

Так как публичной регистрации в системе нет (это внутренний инструмент предприятия), самую первую учётную запись администратора нужно создать один раз командой прямо в контейнере:

```bash
docker compose exec -it app npm run create-admin
```

Скрипт спросит ФИО, логин (латиницей) и пароль (минимум 8 символов) и создаст учётную запись администратора. После этого:

1. Войдите в систему под созданной учётной записью.
2. Откройте раздел **«Пользователи»** и создайте учётные записи для остальных сотрудников (администраторов и обычных пользователей).
3. Откройте раздел **«Настройки»** и заполните справочники: категории материалов, единицы измерения, поставщиков и места хранения.
4. Начните добавлять материалы в разделе **«Материалы»** и вносить фактические остатки через **«Поступления»**.

Команду `create-admin` также можно выполнить без вопросов, одной строкой (удобно при автоматизированном развёртывании):

```bash
docker compose exec app npm run create-admin -- --full-name="Иван Иванов" --login=admin --password="ЗамениНаНадёжныйПароль"
```

Если попытаться создать пользователя с логином, который уже занят, скрипт откажется и подскажет управлять учётными записями через раздел «Пользователи».

## Переменные окружения

Полный список — в `.env.example`. Кратко:

| Переменная | Назначение |
|---|---|
| `COMPOSE_PROFILES` | Выбор варианта запуска: `proxy` (со встроенным HTTPS) или пусто (без него) — см. [«Готовые варианты запуска»](#готовые-варианты-запуска) |
| `POSTGRES_PASSWORD` | Пароль базы данных PostgreSQL внутри Docker-сети |
| `AUTH_SECRET` | Секрет для подписи сессионных cookie. Обязательно должен быть длинным и случайным |
| `AUTH_URL` | Публичный адрес системы в сети предприятия, с `https://` |
| `DATABASE_URL` | Строка подключения к базе данных для локального запуска скриптов вне Docker (см. раздел «Разработка») |
| `NODE_ENV` | `production` при запуске через Docker (задаётся автоматически в `docker-compose.yml`) |

Все значения передаются через переменные окружения и не хранятся в исходном коде.

## Обновление системы

Когда появится новая версия исходного кода:

```bash
git pull            # или другой способ получить новую версию файлов
docker compose up -d --build
```

Структура базы данных обновится автоматически при старте контейнера приложения — существующие данные (материалы, остатки, история операций, пользователи) сохраняются.

## Резервное копирование

Резервное копирование базы данных выполняется штатной утилитой PostgreSQL `pg_dump` через Docker:

```bash
docker compose exec db pg_dump -U materials_app materials > backup_$(date +%Y-%m-%d).sql
```

Рекомендуется настроить эту команду по расписанию (например, через `cron`) и хранить копии отдельно от сервера — например, на резервном диске или файловом сервере предприятия.

Восстановление из резервной копии:

```bash
cat backup_2026-08-08.sql | docker compose exec -T db psql -U materials_app -d materials
```

## Возможности системы

- **Учётные записи и права доступа** — вход по логину и паролю, роли «Администратор» и «Пользователь», отключение доступа без потери истории операций сотрудника.
- **Карточки материалов** — наименование, категория, единица измерения, минимальный остаток, комментарий. Материалы не удаляются, а переносятся в архив.
- **Справочники** — категории, единицы измерения, поставщики, места хранения; редактируются в разделе «Настройки».
- **Учёт по местам хранения** — один материал может храниться в нескольких местах, общий остаток считается автоматически.
- **Поступления** — оформление прихода материала с указанием количества, стоимости, поставщика, места хранения; подбор материала по названию с автодополнением.
- **Списания** — списание материала со склада; **система физически не позволяет списать больше, чем есть в наличии**, даже если несколько человек работают одновременно.
- **Поиск и фильтры** — по названию материала, категории, месту хранения; карточка материала показывает остатки по всем местам хранения и полную историю операций.
- **Контроль остатков** — настраиваемый минимальный остаток по каждому материалу, автоматический список «Требуется закупка» с цветовой индикацией статуса (в норме / ниже минимума / нет остатка).
- **История операций** — дата, время, пользователь, тип операции, количество, место хранения, поставщик, комментарий и остаток после операции — для каждого движения материала.
- **Адаптивный интерфейс** — удобно работать как за компьютером, так и с планшета или телефона; тема оформления (светлая/тёмная) подстраивается под настройки браузера/операционной системы или переключается вручную.
- **Безопасность** — проверка прав доступа на сервере при каждом действии, надёжное хранение паролей, защита от подбора пароля, защитные заголовки браузера, архивирование вместо удаления данных.

## Технологии

- **Next.js** + **React** + **TypeScript** — веб-приложение (интерфейс и сервер в одном проекте).
- **PostgreSQL** — база данных.
- **Drizzle ORM** — доступ к базе данных и миграции структуры.
- **Auth.js** — вход в систему; пароли хранятся в виде хэша **Argon2id**.
- **shadcn/ui + Tailwind CSS** — интерфейс.
- **Docker / Docker Compose** — упаковка и запуск на сервере.
- **nginx** — прокси-сервер, обеспечивающий HTTPS.

## Структура проекта

```
├── docker/
│   ├── certs/                 # сертификат и ключ для HTTPS (nginx)
│   ├── nginx.conf             # настройка прокси-сервера (HTTPS → приложение)
│   ├── entrypoint.sh          # применяет миграции перед запуском приложения
│   └── init-extensions.sql    # расширения PostgreSQL, применяются при первом старте
├── drizzle/                   # миграции базы данных (создаются автоматически)
├── src/
│   ├── app/                   # страницы приложения
│   ├── components/            # компоненты интерфейса
│   ├── db/                    # схема базы данных, миграции, создание администратора
│   ├── lib/                   # вспомогательные функции, проверка прав, валидация
│   └── server/
│       ├── actions/           # обработчики действий (создание, изменение, удаление)
│       └── services/          # бизнес-логика приложения
├── Dockerfile
├── docker-compose.yml         # запуск на сервере: приложение + база данных + прокси (HTTPS, опционально)
└── .env.example
```

## Разработка

Этот раздел — для тех, кто будет дорабатывать систему, а не для установки на сервере предприятия (см. разделы выше).

Потребуется: Node.js 22+, Docker (для локальной базы данных).

```bash
npm install
cp .env.example .env
# В .env для локальной разработки без прокси и HTTPS укажите:
#   AUTH_URL=http://localhost:3000

# Запустить базу данных локально (порт 5432 будет доступен на localhost)
docker compose -f docker-compose.yml -f docker-compose.override.yml up -d db

npm run db:migrate
npm run dev
```

Полезные команды:

```bash
npm run lint          # проверка кода линтером
npm run build          # проверка продакшен-сборки
npm run db:generate    # создать миграцию после изменения src/db/schema.ts
npm run db:studio      # визуальный просмотр базы данных
npm run create-admin   # создать администратора в локальной базе данных
```

Файл `docker-compose.override.yml` предназначен только для локальной разработки (открывает порт базы данных на `localhost`) и не должен использоваться на сервере предприятия.
